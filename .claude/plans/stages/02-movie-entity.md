# Этап 2 — сущность фильма (`feat/movie-entity`)

Реализовано по TDD: для каждого модуля сначала писался тест, проверялось
падение (`Cannot find module`/красный прогон), затем — реализация до
зелёного прогона. Порядок: `model/schema` → `lib/*` → `ui/movie-card` →
`api/movie-api`. После первой версии этап прошёл ревью (см. «Ревью и
правки» ниже) — исправления внесены тем же циклом, без нового коммита
поверх незамеченных багов.

## Почему так

### Форма ответа API подтверждена, не угадана

До реализации была загружена OpenAPI-схема `api.poiskkino.dev/documentation-json`
и проверены реальные схемы `SearchMovieResponseDtoV1_4`, `SearchMovieDtoV1_4`,
`MovieDtoV1_4`, `Rating`, `ShortImage`, `GenreItem`. Это подтвердило
большинство допущений плана: массив результатов лежит в поле `docs`,
пагинация — `page` / `limit` / `pages` / `total`, постер — `poster.url` /
`poster.previewUrl`, рейтинг — `rating.kp` / `rating.imdb`. Но не «id
обязателен в обеих схемах», как было сформулировано в первой версии этого
документа: `SearchMovieDtoV1_4.required` содержит только `id`, а у полного
`MovieDtoV1_4` `required` вообще пуст, и `id` там помечен `nullable`.
`movieSchema.id` тем не менее обязателен для обоих случаев — не потому,
что так требует спека API, а потому, что без числового id приложению
нечем ни построить ссылку на фильм, ни создать запись коллекции. Это
решение приложения, а не пересказ контракта API — так и написано в
комментарии над `movieSchema` после ревью.

Аналогично `GenreItem` в спеке не объявляет ни одного обязательного поля
(`required` пуст) — первая версия `genreSchema.name` была `z.string()`
без `nullish()`, что роняло бы весь фильм из-за одного жанра без имени.
Исправлено.

### Один битый фильм в выдаче поиска не должен прятать девять остальных

Первая версия валидировала весь ответ поиска одним `movieSearchResponseSchema.parse()`
— один невалидный элемент `docs` проваливал всю выдачу. После ревью
разделено на два уровня:

- `movieSearchEnvelopeSchema` (сейчас `rawResponseSchema` эндпоинта, см.
  ниже) строго проверяет только конверт: `page`/`limit`/`pages`/`total`
  и что `docs` — массив; элементы `docs` в нём намеренно `z.unknown()`;
- `parseMovieDocs()` в `transformResponse` разбирает каждый элемент через
  `movieSchema.safeParse`, отбрасывая невалидные записи с
  `console.warn(...)` (не пустой `catch` — правило CLAUDE.md «ошибки
  видимы»), и оставляя валидные.

Тест `movie-api.test.tsx` подтверждает это на уровне всего эндпоинта:
из двух записей в `docs`, одна без `id`, в результате остаётся одна,
и `console.warn` вызывается.

### `rating.kp === 0` — это отсутствие оценки, а не оценка «0»

Так помечает неоценённые фильмы сам API. `selectRating` поэтому
использует `||`, а не `??`: ноль и `null`/`undefined` трактуются
одинаково — оба означают «оценки нет», и тогда пробуем `imdb`.

### Ошибка валидации схемы — через нативный механизм RTK Query, не через `throw` в `transformResponse`

Первая версия делала `schema.parse(response)` прямо в `transformResponse`.
При невалидном ответе это бросает `ZodError`, а RTK Query не умеет
обрабатывать исключения из `transformResponse` как обычную ошибку
запроса: `error` в результате хука становится непредсказуемым
`SerializedError` с JSON-дампом `ZodError` внутри `message`, и в консоль
дополнительно пишется "An unhandled error occurred processing a
request...". Проверено экспериментально (см. ревью) — компоненту
пришлось бы разбирать два принципиально разных типа ошибок и вручную
защищаться от JSON-дампа в интерфейсе.

Вместо этого используется собственный механизм схем RTK Query 2.x
(пакет `@reduxjs/toolkit` этого проекта его уже поддерживает — Zod 4
реализует `StandardSchemaV1`, который этот механизм ожидает):

- `rawResponseSchema` на каждом эндпоинте — схема, которой проверяется
  сырой ответ до `transformResponse`;
- `onSchemaFailure` (в `shared/api/base-api.ts`) — логирует причину
  (`console.error` с `error.issues`) при провале любой схемы любого
  эндпоинта;
- `catchSchemaFailure` (там же) — превращает провал схемы в обычный
  `FetchBaseQueryError` вида `{ status: "CUSTOM_ERROR", error:
  SCHEMA_VALIDATION_ERROR_MESSAGE }`, той же формы, что и сетевые ошибки.

Это относится к `shared/api`, а не к `entities/movie`: следующий
эндпоинт любой другой сущности получит то же поведение бесплатно, не
переизобретая его.

### `api/movie-api.ts` — модуль этапа с наиболее гибридным TDD

План перечислял для этапа 2 три теста (схема отвергает битый ответ;
карточка рендерит данные; карточка без постера рендерит заглушку) — все
про `model`/`ui`, не про сетевой слой. Решено дополнительно покрыть
`movie-api.ts` тестами через MSW, потому что это единственное место
этапа, где реально происходит сетевой запрос, а `CLAUDE.md` требует
проверки границы API. После ревью тесты дополнены: проверкой параметров
запроса (`query`/`page` — это контракт с API, который можно сломать
молча, если проверять только факт успеха) и формы ошибки при провале
схемы.

### Рейтинг форматируется, а не выводится сырым числом

Кинопоиск отдаёт `kp` вроде `8.489`. Первая версия выводила его в
карточке как есть. `formatRating()` округляет до `RATING_DECIMAL_PLACES`
(1 знак после запятой, вынесено в `config`, а не как магическое число
внутри `toFixed`). Заодно карточка перестала прятать блок рейтинга при
его отсутствии — раньше это расходилось с комментарием у
`UNKNOWN_VALUE_PLACEHOLDER`, который обещал плейсхолдер и для года, и
для рейтинга, а на деле подставлялся только для года. Теперь оба поля
ведут себя одинаково: значение или `—`.

### Временное исключение в `steiger.config.js`

`pnpm lint:fsd` не проходил: правило `fsd/insignificant-slice` считает
`entities/movie` «незначительным», потому что на этот момент ни одна
страница ещё её не импортирует (подключение — на этапах 3–4). Это риск
плана («каждый PR зелёный по всем проверкам»), не закрытый на этапе 1.

Решение, согласованное с пользователем: точечно отключить правило для
`src/entities/movie/**` в `steiger.config.js` (тем же механизмом, что
уже использует `eslint.config.js` для тестовых файлов) с комментарием
о причине. **Снять это исключение сразу в PR этапа 3** (`feat/movie-search`),
как только `pages/search` начнёт использовать `useSearchMoviesQuery`/
`MovieCard` — слайс перестанет быть «незначительным» сам по себе.

### Что не вошло / долг на будущие этапы

- `entities/movie` пока нигде не подключена к дереву приложения — это
  осознанно, подключение на этапах 3 (поиск) и 4 (страница фильма).
- Публичный `index.ts` слайса сейчас экспортирует только хуки, `MovieCard`
  и типы — так и было задумано в плане («index.ts — публичный API: хуки,
  компонент, типы»). Но `widgets/movie-details` на этапе 4 понадобятся
  `selectPosterUrl` + `POSTER_SIZE.full`, `selectRating`, `formatRating` —
  сейчас они не экспортированы наружу (виджет не может импортировать
  `@/entities/movie/lib` напрямую, только корень слайса). **На этапе 4
  доэкспортировать нужное из `entities/movie/index.ts` первым делом**,
  до того как писать сам виджет — иначе он не соберётся.
- Формат ошибок сети/схемы теперь единый (`FetchBaseQueryError`), но
  перевод его в текст для пользователя (разные статусы, `CUSTOM_ERROR`
  и т.д.) — по плану задача этапа 3 (`shared/ui/ErrorMessage`), там же
  появится первый реальный потребитель.
- В репозитории `pnpm format` (`prettier --write .`) сейчас меняет ~40
  файлов, не тронутых в этой ветке — похоже на несовпадение
  `core.autocrlf`/`endOfLine` на Windows, а не на реальные ошибки стиля.
  `pnpm lint` этого не ловит, `format:check` нет ни в скриптах, ни в CI.
  Файлы, изменённые в этой ветке, дополнительно проверены точечно
  (`npx prettier --check`) и приведены в порядок. Останется отдельной
  задачей вне этого этапа: разобраться с line endings и решить, стоит
  ли добавлять `format:check` в CI.

## Тесты

8 test suites, 24 теста (см. `pnpm test`):

- `schema.test.ts` — валидный ответ; ответ с `null`-полями; отказ без
  `id` с внятным сообщением об ошибке; жанр без имени не роняет фильм;
  `parseMovieDocs` отбрасывает невалидные записи и логирует
  предупреждение, оставляя валидные.
- `select-poster-url.test.ts`, `select-rating.test.ts`,
  `format-release-year.test.ts`, `format-rating.test.ts` — граничные
  случаи (нет постера, нулевой рейтинг, отсутствующий год, округление).
- `movie-card.test.tsx` — рендер названия/года/округлённого рейтинга/
  `alt`; заглушка без постера; плейсхолдер без рейтинга.
- `movie-api.test.tsx` — `searchMovies` отправляет `query`/`page` и
  возвращает распарсенный ответ; отбрасывает битые записи `docs`, не
  роняя всю выдачу; `getMovieById` завершается предсказуемой ошибкой
  (`{status: "CUSTOM_ERROR", error: ...}`) на невалидном по схеме ответе.
