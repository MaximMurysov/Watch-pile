## Почему так

### `widgets/movie-grid` переиспользован без изменения пропсов

Так и планировалось (см. `steiger.config.js`, комментарий с этапа 3).
`MovieGrid`/`MovieCard`/`CollectionButton` рассчитаны на полный `Movie`
(`id`, `name`, `year`, `poster: {url, previewUrl}`, `rating`, ...), а
запись коллекции (`CollectionItem`) хранит только `movieId`, `title`,
`posterUrl` — этого не хватает для настоящего `Movie`. Вместо правки
виджета — чистая функция-адаптер `collectionItemToMovie` в
`pages/collection/lib` (не в `entities/*`: это был бы кросс-импорт двух
сущностей, запрещённый правилами FSD, а страница может импортировать обе).
Она заполняет то, что есть, и обнуляет остальное (`year`, `rating`,
`genres`, ...) — `MovieCard` уже рассчитан на `nullish`-поля и рисует для
них плейсхолдеры, поэтому карточка в коллекции показывает название и
постер, прочерк вместо года/рейтинга, без падений.

Осознанно не стали делать наоборот — дотягивать данные по каждому
элементу коллекции через `getMovieById` (RTK Query): это было бы N+1
запросов к API с бесплатным ключом poiskkino.dev ради страницы, которая
по архитектурному решению («коллекция хранится локально») не должна
зависеть от сети для отображения уже сохранённого.

Пагинация виджета не убиралась отдельной веткой кода — `MovieGrid`
вызывается с `page={1}`, `totalPages={1}`, `onPageChange` — заглушка
(`handlePageChangeNoop`, с поясняющим комментарием). `Pagination`
(`shared/ui/pagination.tsx`) уже возвращает `null` при `totalPages <= 1`,
поэтому контролов пагинации на странице коллекции не появляется без
единой правки виджета.

### Пустое состояние — до вызова `MovieGrid`, не через его проп

У `MovieGrid` `emptyMessage` — просто строка, без слота под ссылку.
Чтобы не трогать виджет, страница сама решает: при пустом списке текущей
вкладки рендерит собственный `EmptyState` со ссылкой `<Link
to={ROUTES.search}>`, а `MovieGrid` вызывается только когда список не
пуст (`emptyMessage`/`error`, переданные в этом вызове, поэтому
недостижимы).

### Вкладки — логика страницы, не отдельная фича

Статус — в URL (`?status=want|watched`) через `useSearchParams`, без
`useState`, по тому же архитектурному принципу, что `query`/`page` на
странице поиска. Отдельного `features`-слайса под это не заводили: в
отличие от `features/movie-search` (дебаунс, инпут, клэмп страницы —
несколько частей с независимым юнит-тестированием), здесь — одна строка
чтения параметра и один обработчик клика, используемые только на этой
странице. Валидация статуса — через уже существующую
`collectionStatusSchema.safeParse` из `entities/collection-item`
(невалидное или отсутствующее значение → дефолт `"want"`), не через
новый ad-hoc union.

### Ревью

Ревью `code-reviewer` (diff `main...HEAD`) критичных и важных замечаний
не нашло. Два **[мелочь]** — не о поведении, а предложение подробнее
расписать в этом документе два уже перечисленных выше компромисса
(вызов `MovieGrid` не по полному контракту пропсов; обнуление большей
части полей `Movie` в адаптере). Пользователь решил не расширять текст
сверх того, что уже здесь написано — оставляем как есть, поведение и
тесты замечания не затрагивают.

## Тесты

2 test suite, 5 тестов (94 всего в проекте, было 89 после этапа 6):

- `lib/collection-item-to-movie.test.ts` — маппинг переносит
  `id`/`name`/`poster`, обнуляет остальные поля `Movie`; запись без
  названия/постера → `null`, не пустая строка.
- `ui/collection-page.test.tsx` — happy path: две записи разных статусов,
  на активной вкладке видна только своя карточка, клик по другой вкладке
  меняет список и `?status=` в URL; пустая коллекция → подсказка со
  ссылкой «Искать фильмы» (`href="/"`); невалидный `?status=bogus` не
  роняет страницу, вкладка по умолчанию — «Хочу посмотреть».
