# Контекст проекта

**Watchpile** — приложение для поиска фильмов и ведения личной коллекции.

Функциональность:

- поиск фильмов через API poiskkino.dev (неофициальный API
  Кинопоиска), результаты с пагинацией;
- детальная страница фильма;
- личная коллекция: «хочу посмотреть» / «посмотрел»;
- заметка о фильме: оценка, дата просмотра, теги, текст.

## Стек

- React 19 + TypeScript (strict)
- Vite 8 — сборка
- Redux Toolkit 2 + RTK Query — состояние и работа с API
- React Hook Form + Zod (`@hookform/resolvers`) — формы и валидация
- React Router 7 — роутинг
- Jest + React Testing Library + MSW — тесты
- CSS Modules — стилизация

Версии в `package.json` — источник истины. Если API библиотеки
не совпадает с ожидаемым, читай её типы в `node_modules`, а не
угадывай по памяти.

## Команды

```
pnpm dev        # дев-сервер
pnpm typecheck  # tsc -b --noEmit
pnpm lint       # eslint
pnpm lint:fsd   # steiger — проверка правил слоёв
pnpm test       # jest
pnpm build      # прод-сборка
```

Пакетный менеджер — **pnpm**. Не использовать `npm` и `yarn`:
в репозитории только `pnpm-lock.yaml`. Установка зависимостей —
`pnpm add`, dev-зависимостей — `pnpm add -D`.

## Коммиты

Мы работаем с Git по следующему принципу:

main — основная ветка проекта.
Для каждой отдельной фичи создаём отдельную ветку от актуального состояния main.
Все изменения по фиче выполняем только в её feature-ветке.
После завершения фичи создаём Pull Request в main.
После успешного merge feature-ветку удаляем.
Перед началом следующей фичи используем актуальный main.

Для текущей задачи работай именно в отдельной feature-ветке, не в main

**Язык.** Сообщения git-коммитов (заголовок и тело) и описания Pull
Request — на английском. Всё остальное — код-комментарии, эта
документация, README, файлы в `.claude/plans/`, переписка с
пользователем — на русском.

## Архитектура: Feature-Sliced Design

При вопросах об архитектуре FSD опирайся на
[`.claude/skills/feature-sliced-design/`](./.claude/skills/feature-sliced-design/SKILL.md) —
там подробные рекомендации по слоям, слайсам и правилам.

Слои снизу вверх:
`shared` → `entities` → `features` → `widgets` → `pages` → `app`

```
src/
  app/
    providers/           store-provider, router-provider
    styles/
  pages/
    search/ movie/ collection/
  widgets/
    movie-grid/          карточки + кнопка коллекции
    movie-details/
    header/
  features/
    movie-search/        инпут + синхронизация с URL
    add-to-collection/   кнопка смены статуса
    rate-movie/          форма RHF + Zod
  entities/
    movie/               api (injectEndpoints), model (Zod, типы), ui (карточка)
    collection-item/     model (slice, селекторы, persist)
  shared/
    api/                 baseApi (createApi с пустыми endpoints)
    ui/ lib/ config/
```

### Правила слоёв — нарушать нельзя

- **Импорт только вниз.** Слой может импортировать строго нижние
  слои. Никогда наверх.
- **Никаких кросс-импортов внутри слоя.** Фича не импортирует
  другую фичу, entity — другую entity. Нужен общий код — опускай
  его в нижний слой.
- **Только публичный API.** Импорт из корня слайса
  (`@/entities/movie`), не из его внутренностей
  (`@/entities/movie/ui/movie-card`). У каждого слайса есть
  `index.ts` — реэкспорт того, что открыто наружу.
- **Сегменты слайса**: `ui`, `model`, `api`, `lib`, `config`.
  Отдельной папки `hooks` нет — хуки живут в `model`.

### Что где лежит

- `entities` — описание сущности: схема, тип, как выглядит.
  Сущность ничего не «делает».
- `features` — действие пользователя: искать, добавить, оценить.
- `widgets` — композиция entity + feature в готовый блок.
- Если не понятно, entity это или feature — спроси, не угадывай.

Соблюдение правил проверяется линтером `steiger`. Он должен быть
зелёным перед завершением задачи.

## Архитектурные решения

Обновляется по мере принятия решений. Не переизобретать заново.

- **Серверные данные — только через RTK Query.** Никаких
  `useEffect + fetch`. `baseApi` лежит в `shared/api` с пустым
  `endpoints`, конкретные эндпоинты добавляются через
  `injectEndpoints` в `entities/<name>/api`. Инвалидация — теги.
- **Ответы API валидируются через Zod** в `transformResponse`.
  Типы данных выводятся из схем (`z.infer`), не пишутся руками.
- **Параметры поиска и пагинация живут в URL** (`useSearchParams`),
  не в `useState`. Ссылку можно скопировать, «назад» работает.
- **Redux-слайсы — только для клиентского состояния** (UI, фильтры,
  которых нет в URL). Серверные данные в слайсы не дублируются.
- **Формы — только React Hook Form + `zodResolver`.** Схема Zod —
  единственный источник и валидации, и типа формы.
- **Коллекция** хранится локально; синхронизация с бэкендом
  пока не планируется.
- **Источник данных о фильмах — poiskkino.dev** (неофициальный API
  Кинопоиска, бывший kinopoisk.dev — переименован из-за товарного
  знака «Кинопоиск»), не TMDB. Почему: регистрация на themoviedb.org
  недоступна из РФ, включая через VPN. Как применять: базовый URL и
  ключ — в `shared/config`/`shared/config/env`, авторизация header'ом
  `X-API-KEY`. Ответы этого API — единственный источник для
  `entities/movie`, TMDB не используется вовсе.

## Тесты

- **Новый функционал — по TDD.** Сначала падающий тест на нужное
  поведение (red), потом минимальный код, чтобы он прошёл (green),
  потом рефакторинг при необходимости. Не писать реализацию раньше
  теста, который её описывает.
- Каждая законченная фича — минимум два теста: happy path
  и поведение при ошибке API.
- Сеть мокается через MSW. Не мокать `fetch` вручную, не мокать
  сами хуки RTK Query.
- Тестируем поведение, а не реализацию: запросы через роли и
  тексты, доступные пользователю, не через `data-testid` без нужды.
- Компоненты рендерятся с обёрткой из `Provider` + `MemoryRouter`.
  Обёртка — одна переиспользуемая утилита в `src/shared/lib/test`.

## Рабочий процесс

- **Для нетривиальной задачи сначала план**, не код: какие файлы
  затрагиваем, какие есть варианты, какие компромиссы. Код — после
  явного «ок».
- **Одна задача за раз.** Не делать попутных улучшений, о которых
  не просили. Минимальный диф.
- **Новые зависимости — только спросив.** Сначала проверить, что
  уже установлено.
- **Не выполнять git-команды** (`commit`, `push`, `reset`, `checkout`)
  без явного запроса.
- **Не выдумывать API.** Не уверен — прочитать типы или документацию.
- **Не делать тихих допущений.** Если вариантов несколько — показать
  их с плюсами и минусами и спросить.
- **По завершении задачи — отметить прогресс в `.claude/plans/checklist.md`**:
  проставить `[x]` у выполненных пунктов этапа, дописать то, что
  изменилось по факту работы (найденные на ревью правки, отклонения от
  плана), сразу отметить пункт «PR → merge → удаление ветки» как
  выполненный. Это отдельный шаг от чек-листа ниже — тот проверяет
  качество кода, этот фиксирует прогресс по плану.
- **Отметка прогресса — в том же коммите(ах), что и код фичи, до
  открытия PR.** Не делать отдельный коммит/PR только ради галочки
  «этап сделан» после merge — к моменту, когда работа завершена и чек-лист
  из CLAUDE.md зелёный, PR и его merge можно считать формальностью,
  дополнительный коммит для этого не нужен.

# Правила кода

1. **Имена**: понятные, без сокращений. Существительные для данных,
   глаголы для действий. Boolean — `is/has/can/should`.
   Файлы — `kebab-case`, компоненты — `PascalCase`, хуки — `useXxx`.

2. **Один файл — одна ответственность.** Файл < 300 строк,
   функция < 30 строк, вложенность ≤ 3. Если в названии есть «и» —
   разделить.

3. **Без `any`, `@ts-ignore`, `@ts-nocheck`** (кроме сгенерированного
   кода). Точные типы или `unknown` + type guard. У публичных функций
   возвращаемый тип указан явно.

4. **Без магических значений.** Числа и строки → именованные константы.

5. **Ошибки видимы.** Пустой `catch {}` запрещён. Логировать или
   показывать пользователю.

6. **Валидация на границе** (ответ API, форма, парсинг). Внутри —
   доверяем типам.

7. **Чистые функции** для утилит. Side effects изолированы в
   api/model-слое.

8. **Иммутабельность**: `const` по умолчанию, аргументы и state не
   мутировать. Исключение — `createSlice`, там Immer.

9. **Early return** вместо вложенных `if/else`.

10. **Комментарии — про «почему»**, не «что». Очевидные не писать.

11. **DRY с умом**: дублирование 3+ раз → выносить. 1–2 раза —
    оставить.

12. **Импорты**: внешние → алиасы (`@/`) → относительные. Между
    группами пустая строка.

13. **Секреты — в `.env`**, в репозитории `.env.example`. Ключи
    никогда не хардкодить.

14. **Читаемость > краткости.** Длинное понятное имя лучше короткого
    хитрого.

Также запрещено: закомментированный код (git помнит), циклические
зависимости, преждевременная оптимизация и абстракция, создание
файлов в `node_modules`, `dist`, `coverage`.
